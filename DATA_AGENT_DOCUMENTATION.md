# DATA_AGENT: Technical Architecture & System Documentation

## 1. Executive Summary & Overview

**DATA_AGENT** is an autonomous, multi-agent AI system designed for data engineering, database querying (Text-to-SQL), and ETL automation. Built using **LangGraph**, **LangChain**, **Pydantic**, **PostgreSQL**, and **Pandas**, the system utilizes a stateful hierarchical graph architecture to interpret natural language requests and execute complex data tasks safely and reliably.

### Key Capabilities
- **Hierarchical Routing:** A master router classifies intent and delegates tasks to specialized domain-specific sub-agents.
- **Guardrailed Text-to-SQL:** Converts natural language queries into Postgres SQL after inspecting live schema metadata (tables, data types, and sample rows), then evaluates query safety using a dedicated **Security Judge Node** to prevent destructive operations (`DROP`, `DELETE`, `UPDATE`, `ALTER`, `TRUNCATE`).
- **Autonomous ETL Automation:** Extracts raw data from API endpoints, normalizes JSON into tabular formats (CSV, JSON, Parquet), dynamically previews data context, and synthesizes/executes Pandas transformation scripts in a sandboxed Python environment.

## 3. Data Schemas & State Management (`models/schema.py`)

All state transitions and node outputs are governed by strict Pydantic schemas:

### 3.1 `DataAgentSchema`
Governs the top-level state of the Master Router:
- `messages` (`list`): Message history accumulated during conversation.
- `route_response` (`str`): Classification result (`"sql"` or `"etl"`).

### 3.2 `RouterSchema`
Pydantic model used for structured LLM routing output:
- `answer` (`Literal["sql", "etl"]`): Selected destination sub-agent.
- `comments` (`str`): Explanation for why the query was classified as SQL or ETL.

### 3.3 `AgentSchema`
State schema for the **SQL Analyst Agent**:
- `messages` (`list`): Conversational trace.
- `user_question` (`str`): Original natural language query.
- `curated_ques` (`str`): Cleaned and standardized user question.
- `prompt_query_context` (`str`): Consolidated prompt containing database schema and sample rows.
- `generated_sql_query` (`str`): Raw SQL generated by the LLM.
- `is_safe_sql_response` (`str`): Safety verdict (`"Yes"` or `"No"`).
- `comments` (`str`): Feedback from the security judge.
- `sql_query_execution_result` (`str`): Stringified query execution result from PostgreSQL.
- `final_answer` (`str`): User-facing natural language response.

### 3.4 `JudgeSchema`
Structured output schema for the Security Judge Node:
- `answer` (`Literal["Yes", "No"]`): Whether the SQL statement is safe (read-only) or unsafe (write/modify/drop).
- `comments` (`str`): Explanation of safety determination.

### 3.5 `ETLAgentSchema`
State schema for the **ETL Analyst Agent**:
- `messages` (`list`): Message thread containing user prompts, AI responses, and Tool Messages.

## 4. Component Deep Dive & Agent Implementation

### 4.1 Master Router Agent (`agents/data_agent.py`)
- **Router Node (`router_node`):** Uses an LLM with structured output (`RouterSchema`) to determine whether the user wants database reporting (SQL) or data extraction/transformation (ETL).
- **Conditional Edge (`route_edge`):** Directs state to `etl_node` or `sql_node`.
- **Delegation:** Invokes the respective sub-agent state graph (`sql_analyst.invoke()` or `etl_analyst.invoke()`) synchronously and appends the response to state.

### 4.2 SQL Analyst Sub-Graph (`agents/sql_analyst.py`)
The SQL Analyst is implemented as a 7-stage state machine:

1. **`curate_ques`**: Refines the raw input question for clarity.
2. **`prompt_query_context`**: Instantiates `DatabaseUtil` to extract active PostgreSQL schema details (tables, columns, types) and top 5 sample records from the `public` schema. Builds an context-aware prompt. Limits queries to 10 rows by default.
3. **`generate_sql`**: Invokes LLM to produce raw Postgres-compatible SQL code.
4. **`is_safe_sql`**: Evaluates the generated SQL query against security policies using `JudgeSchema`.
5. **Conditional Routing (`is_safe_sql_edge`)**:
   - If **`"Yes"`** -> Proceeds to `execute_sql`.
   - If **`"No"`** -> Routes to `canceled_query`, halting execution and notifying the user that the query was canceled due to security restrictions.
6. **`execute_sql`**: Executes the approved SQL statement against PostgreSQL via `psycopg2` and returns raw tabular data.
7. **`represent_final_answer`**: Synthesizes the raw PostgreSQL result into a clear, natural language answer.

### 4.3 ETL Analyst Sub-Graph (`agents/etl_analyst.py`)
The ETL Agent is a tool-calling graph bound to custom tools:

- **Tools:**
  - `extract_load_tool(url, output_folder, format)`: Makes HTTP requests to REST APIs, normalizes JSON payloads with Pandas (`pd.json_normalize`), and exports them to CSV, JSON, or Parquet files.
  - `transform_load_tool(input_file_path, output_folder, output_format, user_question)`: Reads the dataset, previews the top 3 rows as schema context, requests custom Pandas transformation Python code from the LLM, and executes the code dynamically using a sandboxed `exec()` environment (`ETLTools.execute_code`).
- **Graph Nodes:**
  - `llm_node`: LLM bound with tools (`extract_load_tool`, `transform_load_tool`).
  - `tool_node`: Executes tool calls and returns `ToolMessage` outputs back into state loop until completion.

## 5. Utilities & Helper Modules

### 5.1 Database Utility (`utils/database.py`)
`DatabaseUtil` wraps `psycopg2` database interactions:
- `schema_details(schema_name)`: Queries `information_schema.tables` and `information_schema.columns` to build a schema context string containing table names, column names, data types, and top 5 sample rows for every table.
- `execute_sql(query)`: Safely opens a connection, executes the SQL string, fetches results, commits, and closes cursors cleanly.

### 5.2 ETL Tools Utility (`utils/etl_tools.py`)
`ETLTools` handles disk I/O and dynamic execution:
- `extract_load()`: API fetching with error handling and format-specific serialization (`to_csv`, `to_json`, `to_parquet`).
- `transform_load_context()`: Reads files based on extension (`.csv`, `.json`, `.parquet`) and returns `df.head(3)`.
- `execute_code()`: Executes generated Pandas Python code using `exec()` with clean error handling.

### 5.3 Multi-Tier LLM Selection (`utils/llm_pick.py`)
Provides model selection based on compute/complexity requirements:
- `"low"`: Lightweight LLM (`gpt-5.6-luna`) for fast question curation and synthesis.
- `"medium"`: Medium tier LLM (`gpt-5.6-terra`) for routing, SQL generation, and code generation.
- `"high"`: High-capacity tier (`gpt-5.6-sol`) for complex reasoning tasks.
- `"claude"`: `ChatAnthropic(model_name="claude-sonnet-5")`.

## 6. Security & Guardrail Engineering

Security is a core design pillar of **DATA_AGENT**:

1. **SQL Injection & Data Mutation Guardrail:** The SQL Judge (`is_safe_sql`) strictly forbids any SQL statement containing data modification or structure alteration commands (`INSERT`, `UPDATE`, `DELETE`, `DROP`, `ALTER`, `TRUNCATE`, `CREATE`).
2. **Schema Isolation:** The agent is scoped to specific schema boundaries (`public` by default).
3. **Row Limit Enforcement:** Prompts mandate automatic row truncation (`LIMIT 10`) to prevent out-of-memory errors or database strain during large table queries.
4. **Structured Decision Output:** Router and Judge decisions use Pydantic `BaseModel` schemas to eliminate non-deterministic parsing errors.

## 8. Usage Scenarios & Execution Examples

### Scenario 1: API Extraction and Data Loading
**Input:** 
> "I want to extract data from 'https://pokeapi.co/api/v2/pokemon' and save it to data/extract folder in CSV format."

**System Action:**
1. Master Router identifies request as `"etl"`.
2. `etl_analyst` selects `extract_load_tool`.
3. Tool fetches JSON, flattens payload with `pd.json_normalize`, saves file to `data/extract/extracted_data.csv`.

### Scenario 2: Safe Natural Language SQL Query
**Input:** 
> "What are the different types of Payment Methods in our database?"

**System Action:**
1. Master Router identifies request as `"sql"`.
2. `sql_analyst` curates question and fetches PostgreSQL schema + sample rows.
3. Generates SQL: `SELECT DISTINCT payment_method FROM payments LIMIT 10;`.
4. Security Judge evaluates query: `"Yes"` (Safe read-only query).
5. Query executes on database; result is formatted into natural language response.

### Scenario 3: Unsafe SQL Query Blocking
**Input:** 
> "Drop the customers table from the database."

**System Action:**
1. Master Router identifies request as `"sql"`.
2. `sql_analyst` generates: `DROP TABLE customers;`.
3. Security Judge evaluates query: `"No"` (Destructive SQL command detected).
4. System routes to `canceled_query` node and returns safety warning message without touching the database.
